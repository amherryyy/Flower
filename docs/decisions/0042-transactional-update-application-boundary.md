# ADR 0042: Transactional Update Application Boundary

## Status

Accepted for the first F7 update-application slice.

## Context

F6 produces digest-protected update plans, deterministic manifest and module-configuration migrations, and generated-text three-way merges. It deliberately does not mutate a user's project. The RoomScouter pilot demonstrated the practical consequence: a corrected generated security baseline and a protected product-display-name migration could be planned conceptually but could not be applied through Flower without editing protected files.

The full update workflow also includes package-manager and database effects. Combining every effect in the first filesystem transaction would make rollback claims difficult to verify and would delay the most immediate pilot requirement.

## Decision

- Add a kernel-owned `applyUpdatePlan` boundary over a verified F6 `UpdatePlan`.
- In the first slice, support versioned project, lock, and ownership manifest migrations; mapped module-configuration migrations; and generated-file create, replace, three-way merge, and removal.
- Recompute migration chains from the current documents and registered definitions. Reject changed plans, definitions, source documents, generated bases, generated targets, or current generated bytes before mutation.
- Recheck the current ownership manifest and permit generated-file effects only on paths still classified as generated and replaceable.
- Require every declared approval and a supplied verification runner whenever the plan declares verification commands.
- Write a started journal before mutation and a completed, failed, or partial journal afterward. Journals contain plan identity and path evidence, not file contents or application inputs.
- Apply files in deterministic path order through temporary files. On any mutation, verification, or completion-journal failure, restore every applied path in reverse order.
- Report incomplete restoration distinctly with exit-compatible error metadata.
- Reject plans containing dependency changes or database migrations with `update.unsupportedEffect`. Later F7 slices must add explicit adapters and failure-injection evidence before those effects are accepted.
- Keep command parsing and persisted plan selection outside this kernel slice. The later CLI boundary will load a previously reviewed plan by identity rather than silently replanning during application.

## Consequences

- Flower can now transactionally apply the pilot-derived metadata and generated security-policy changes without overwriting project-owned code.
- Filesystem mutation reuses F6 planning, migration, merge, digest, and ownership contracts instead of creating a second update model.
- The limitation around packages and databases is visible and fail-closed. This slice does not yet satisfy the complete F7 exit criterion or expose the final `flower update` CLI.
- Verification commands remain data in the plan; an application integration must execute them through an approved runner rather than allowing the kernel to interpret arbitrary shell text.
- A future slice still needs persisted plan artifacts, idempotent completed-plan replay, package-manager rollback, database approval boundaries, and recovery behavior across effects that cannot be atomically restored.

## Rejected alternatives

- Editing protected pilot metadata manually was rejected because it bypasses plan identity, ownership, and rollback.
- Trusting caller-provided final bytes without recomputing migrations and merges was rejected because the applied result would not be derived from the reviewed F6 evidence.
- Applying package and database effects without dedicated adapters was rejected because a filesystem backup cannot roll them back truthfully.
- Executing verification strings directly through a shell was rejected because a plan would become an arbitrary command-execution channel.
- Updating generated paths based only on the plan's earlier ownership result was rejected because ownership may change after planning.

## Review triggers

Review when persisted plan storage and CLI application are added, when package-manager or database effects enter the transaction, or before the F7 exit audit.
