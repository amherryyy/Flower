# Flower Framework Specification

**Status:** Draft 0.1  
**Working name:** Flower  
**Specification date:** 2026-09-18  
**Ownership:** Independent, user-owned implementation  

## 1. Purpose

Flower is a development framework for creating, maintaining, and upgrading structured software projects with reliable AI assistance.

Flower combines:

- a small framework kernel;
- a cross-platform command-line interface;
- versioned project and module manifests;
- thin project templates;
- optional reusable capability modules;
- database migration and security validation;
- architecture and ownership enforcement;
- deterministic development workflows;
- generated adapters for AI coding tools;
- an explicit project upgrade system.

Flower is intended to help a developer start projects quickly without losing architectural clarity, security, project ownership, or the ability to upgrade shared foundations.

## 2. Clean-room boundary

Flower is an original implementation informed by general engineering lessons observed in a downstream project audit.

Flower must not copy private framework source code, proprietary prompts, undisclosed workflows, naming systems, or hidden implementation details. Similar engineering problems must be solved through Flower's own specification, terminology, schemas, CLI, tests, and source code.

Allowed inputs include:

- public platform documentation;
- public open-source packages and standards under compatible licenses;
- general software architecture practices;
- observable requirements and failure modes from projects the user is authorized to inspect;
- independently written designs and implementations.

## 3. Goals

Flower must:

1. Create a new project from a thin, testable template.
2. Record project identity and framework state in a machine-readable manifest.
3. Add and remove optional capabilities without copying a monolithic starter.
4. Separate framework-owned, generated, and project-owned code.
5. Enforce architectural dependency and ownership rules.
6. Make database migrations reviewable, reproducible, and testable.
7. Provide secure defaults for authentication, tenancy, authorization, logging, and secrets.
8. Support AI coding tools without making any one model or vendor the source of truth.
9. Make framework updates explicit, reviewable, and reversible.
10. Work consistently on Windows, macOS, Linux, and CI.
11. Keep the framework kernel small enough to understand and maintain.
12. Allow projects to leave the framework without becoming unusable.

## 4. Non-goals

Flower will not initially:

- support every frontend or backend stack;
- provide a no-code application builder;
- autonomously deploy or modify production systems without approval;
- treat AI prompts as executable security boundaries;
- ship billing, AI, scheduling, analytics, and industry modules in the kernel;
- synchronize arbitrary application files from a template repository;
- replace Git, package managers, database migration tools, or hosting platforms;
- require a permanent connection to a central Flower service;
- promise automatic conflict resolution for project-owned code.

## 5. Core principles

### 5.1 Machine-enforced contracts

If a rule protects architecture, data, ownership, or security, it must be enforced by code or tests. Documentation may explain a rule but must not be its only enforcement mechanism.

### 5.2 Small kernel, optional modules

The kernel owns project lifecycle and validation. Product capabilities are independently versioned modules.

### 5.3 Explicit ownership

Every managed path must be classified as:

- `framework`: maintained through versioned packages or migrations;
- `generated`: regenerated by Flower and not manually edited;
- `project`: fully owned by the application;
- `protected`: changeable only through an explicit workflow;
- `local`: never committed or synchronized.

### 5.4 Packages before copied runtime code

Reusable runtime behavior should normally live in versioned packages. Generated source is appropriate for project entry points, configuration, composition roots, and code the project is expected to own.

### 5.5 Plans before writes

Consequential commands must produce a plan before changing files, dependencies, Git state, databases, or external services.

### 5.6 Safe failure

Interrupted workflows must leave a journal that explains what completed, what failed, and how to resume or roll back.

### 5.7 Agent neutrality

Flower owns workflows and project contracts. Claude, Codex, or another coding agent is an adapter and executor, not the framework definition.

### 5.8 Escape is a feature

A project can eject generated integration code or stop using Flower while retaining a normal, understandable application repository.

## 6. Operating modes

Flower has three explicit modes.

### 6.1 Framework mode

Used while developing Flower itself.

```json
{
  "mode": "framework"
}
```

Framework mode permits changes to the kernel, CLI, schemas, official modules, templates, migrations, and adapter generators.

### 6.2 Project mode

Used in an application created or adopted by Flower.

```json
{
  "mode": "project"
}
```

Project mode protects framework metadata and generated outputs while leaving domain code under project ownership.

### 6.3 Module mode

Used while developing a reusable Flower capability.

```json
{
  "mode": "module"
}
```

Module mode validates compatibility, migrations, configuration, generated files, exports, and module-specific tests.

Mode is declared in a manifest. Folder names and Git remote names may be checked as diagnostic signals but never determine mode.

A Flower-managed application contains a small `.flower` control directory.

```text
application/
|
+-- .flower/
|   +-- project.json
|   +-- lock.json
|   +-- ownership.json
|   +-- decisions/
|   +-- generated/
|   +-- journal/
|   `-- cache/                 ignored by Git
|
+-- docs/
|   +-- PROJECT_CONTEXT.md
|   +-- architecture/
|   +-- decisions/
```

The project remains a normal application. `.flower` stores Flower-specific state without taking ownership of the entire repository.

## 9. Canonical project manifest

Path:

```text
.flower/project.json
```

Initial shape:

```json
{
  "$schema": "https://flower.dev/schemas/project/v1.json",
  "schemaVersion": 1,
  "mode": "project",
  "project": {
    "id": "sample-property-app",
    "name": "Sample Property App",
    "description": "Property operations application",
    "domain": "property-management"
  },
  "flower": {
    "version": "0.1.0",
    "channel": "stable"
  },
  "stack": {
    "language": "typescript",
    "runtime": "node",
    "web": "nextjs",
    "database": "supabase-postgres",
    "packageManager": "npm"
  },
  "modules": {
    "auth": "1.0.0",
    "organizations": "1.0.0",
    "rbac": "1.0.0",
    "audit": "1.0.0"
  },
  "capabilities": {
    "multiTenant": true,
    "ai": false,
    "billing": false
  },
  "quality": {
    "minimumCoverage": 80,
    "requireArchitectureCheck": true,
    "requireSecurityCheck": true
  },
  "adapters": {
    "codex": true,
    "claude": false,
    "githubActions": true
  }
}
```

### 9.1 Manifest rules

- Unknown fields are rejected unless the schema explicitly permits an extension namespace.
- Every breaking schema change increments `schemaVersion`.
- Framework version and module versions are separate.
- Secrets are forbidden in the manifest.
- A manifest update is validated before it is written.
- Modules may extend configuration only within their declared namespace.
- Project identity is not inferred from package name, directory, remote, or hosting provider.

## 10. Lock file

Path:

```text
.flower/lock.json
```

The lock file records reproducible state:

```json
{
  "lockVersion": 1,
  "flowerVersion": "0.1.0",
  "template": {
    "id": "next-supabase",
    "version": "0.1.0",
    "digest": "sha256:..."
  },
  "modules": {
    "auth": {
      "version": "1.0.0",
      "digest": "sha256:...",
      "migrations": ["auth-001"]
    }
  },
  "generatedFiles": {
    "src/flower/modules.ts": "sha256:..."
  }
}
```

The lock file must never contain credentials, local paths, or agent conversation history.

## 11. Ownership model

Path:

```text
.flower/ownership.json
```

Example:

```json
{
  "version": 1,
  "rules": [
    {
      "pattern": ".flower/generated/**",
      "owner": "generated",
      "policy": "replace-if-unmodified"
    },
    {
      "pattern": "src/domain/**",
      "owner": "project",
      "policy": "never-overwrite"
    },
    {
      "pattern": "database/migrations/flower/**",
      "owner": "protected",
      "policy": "migration-engine-only"
    },
    {
      "pattern": ".flower/cache/**",
      "owner": "local",
      "policy": "never-commit"
    }
  ]
}
```

Flower validates overlapping patterns, missing coverage for generated files, and attempts to modify protected paths outside their workflow.

## 12. Module system

Each module is independently versioned and contains a module manifest.

```text
modules/auth/
|
+-- flower.module.json
+-- package/
+-- generators/
+-- migrations/
+-- policies/
+-- tests/
+-- docs/
`-- CHANGELOG.md
```

### 12.1 Module manifest

```json
{
  "$schema": "https://flower.dev/schemas/module/v1.json",
  "schemaVersion": 1,
  "id": "auth",
  "version": "1.0.0",
  "compatibleFlower": ">=0.1.0 <0.2.0",
  "dependsOn": {},
  "conflictsWith": [],
  "provides": ["identity", "session"],
  "configurationSchema": "./schemas/config.json",
  "migrations": ["auth-001"],
  "generatedPaths": ["src/flower/auth.ts"],
  "requiredChecks": ["auth-contract", "rls-auth"]
}
```

### 12.2 Module requirements

Every official module must declare:

- compatible Flower versions;
- dependencies and conflicts;
- public API and capabilities;
- configuration schema;
- package dependencies;
- generated files;
- database migrations;
- ownership rules;
- architecture permissions;
- security invariants;
- installation, upgrade, removal, and ejection behavior;
- automated tests and fixtures;
- human-readable documentation.

### 12.3 Initial official modules

Flower 0.1 should include only:

1. `auth`
2. `organizations`
3. `rbac`
4. `audit`

AI chat, scheduling, notifications, billing, analytics, and BIR support remain future optional modules.

## 13. Tenant and authorization model

The initial SaaS profile uses explicit membership.

```text
auth_user
    |
    v
organization_membership
    |
    +--> organization
    `--> role
```

Required tables:

```text
organizations
organization_memberships
roles
role_permissions
audit_events
```

Rules:

- Users are not administrators globally.
- Authorization is evaluated within an organization.
- An organization may have multiple owners/admins.
- The final-owner rule applies per organization.
- Domain records carry `organization_id` directly or inherit it through a validated parent relationship.
- Cross-tenant foreign keys must be impossible or rejected by constraints/triggers.
- Service-role operations must be narrow, named, logged, and tested.
- UI visibility is not authorization.

## 14. Architecture contract

Flower starts with this dependency direction:

```text
interface -> application -> domain
                          -> ports
infrastructure ----------> ports
composition root --------> all layers
```

Recommended project structure:

```text
src/
|
+-- app/                    framework-specific interface and routes
+-- modules/
|   `-- <domain>/
|       +-- domain/
|       +-- application/
|       +-- infrastructure/
|       +-- interface/
|       `-- tests/
+-- shared/
+-- flower/                 generated composition files
`-- bootstrap/
```

### 14.1 Enforced rules

- Domain code cannot import React, Next.js, Supabase, or generated database clients.
- Application code may depend on domain types and declared ports.
- Infrastructure implements ports and may use platform SDKs.
- Interface code calls application use cases, not raw database clients.
- Modules import another module only through declared public exports.
- Cyclic module dependencies fail validation.
- Generated composition code may connect implementations at the boundary.

Exceptions require a recorded architecture decision with an expiry/review field.

## 15. CLI design

The working executable name is:

```text
flower
```

Package naming will be finalized before public publishing.

### 15.1 Core commands

```text
flower init
flower adopt
flower doctor
flower validate
flower add <module>
flower remove <module>
flower eject <module>
flower generate
flower architecture check
flower security check
flower db plan
flower db apply
flower update --plan
flower update --apply <plan-id>
flower workflow run <workflow>
flower adapter generate
flower status
```

### 15.2 Command behavior

All mutating commands follow:

```text
inspect -> validate -> plan -> approve -> apply -> verify -> journal
```

Non-interactive CI mode requires an already generated plan or an explicit safe flag. Interactive confirmation must never be simulated by an agent.

### 15.3 Exit codes

```text
0  success
1  validation or operation failure
2  invalid arguments
3  user approval required
4  incompatible version
5  ownership conflict
6  security policy failure
7  migration failure
8  partial application; recovery journal written
```

Output supports both human-readable text and stable JSON.

## 16. Initialization

`flower init` creates a new project through a transaction.

### 16.1 Inputs

- project name and identifier;
- target directory;
- template;
- package manager;
- selected modules;
- tenancy choice;
- enabled agent adapters;
- Git initialization preference.

### 16.2 Pipeline

```text
environment check
    -> input validation
    -> project plan
    -> directory reservation
    -> template materialization
    -> dependency installation
    -> module installation
    -> manifest and lock generation
    -> adapter generation
    -> tests, type-check, lint, build
    -> initialization journal
```

### 16.3 Safety properties

- Refuse a non-empty target unless `--adopt` is used.
- Never delete an existing `.git` directory.
- Never create or push a remote automatically.
- Never write real secrets into tracked files.
- Roll back newly created files when initialization fails before commit point.
- Keep a recovery journal when complete rollback is impossible.
- Support `--dry-run` and `--json`.
- Be idempotent after successful initialization.

## 17. Adoption

`flower adopt` adds Flower to an existing project.

It must:

1. inspect the project without changing it;
2. identify stack, package manager, database paths, CI, and Git state;
3. report incompatible or ambiguous conditions;
4. create an adoption plan;
5. classify existing files as project-owned by default;
6. add only explicit Flower metadata and selected modules;
7. avoid replacing existing CI or agent instructions without a reviewed merge;
8. verify the resulting project;
9. journal every applied change.

## 18. Workflow engine

Workflows are data validated by a schema, not free-form prompt files.

Example conceptual workflow:

```yaml
id: feature
version: 1
inputs:
  - taskId
  - summary
steps:
  - id: preflight
    action: project.validate
    writes: []
  - id: plan
    action: feature.plan
    writes:
      - .flower/journal/**
  - id: approve
    action: approval.require
  - id: implement
    action: agent.delegate
    ownership:
      allow:
        - project
  - id: verify
    action: checks.run
    checks:
      - tests
      - typecheck
      - lint
      - architecture
      - security
  - id: record
    action: verification.write
```

### 18.1 Workflow guarantees

- Schemas validate inputs and allowed actions.
- Every step declares permitted reads, writes, and external side effects.
- Approval steps cannot be bypassed by adapters.
- A journal stores status and resumability.
- Workflows may call agents, but agents receive scoped tasks and ownership limits.
- Workflow definitions never contain secrets.
- External mutations are isolated in explicit actions.

## 19. AI adapter system

The canonical sources are:

- `.flower/project.json`;
- `.flower/ownership.json`;
- architecture policies;
- workflow definitions;
- project context and decisions.

Adapters generate tool-specific files such as:

```text
AGENTS.md
CLAUDE.md
.codex/... 
.claude/...
```

### 19.1 Adapter rules

- Generated files include their generator version and input checksum.
- Editing a generated adapter causes `flower validate` to report drift.
- Project-specific agent notes live in a separate user-owned file included by adapters.
- Adapters cannot weaken ownership, security, or approval rules.
- Missing tool capabilities must be reported rather than silently simulated.
- Agent memory and conversation caches are local and ignored by Git.
- Flower must function without any AI adapter.

## 20. Migration system

Database changes use immutable, versioned migration units.

```text
database/migrations/
|
+-- flower/
|   +-- auth-001.sql
|   +-- organizations-001.sql
|   `-- rbac-001.sql
`-- project/
    `-- 202609180001-create-properties.sql
```

### 20.1 Migration manifest

Each migration records:

- ID and checksum;
- owning module or project;
- dependencies;
- compatible database provider;
- transaction support;
- destructive-change classification;
- verification queries;
- rollback guidance;
- RLS and privilege expectations.

### 20.2 Required behavior

- Applied migration checksums cannot change.
- Destructive changes require explicit approval.
- Production application requires a previously generated plan.
- Framework migrations and project migrations use separate namespaces.
- Generated database types refresh only after verified application.
- Schema drift is detected before updates.
- RLS tests run against an isolated test database.
- No command claims success until verification queries pass.

## 21. Update system

Flower updates packages, modules, generated integration files, schemas, and migrations without replacing arbitrary project code.

### 21.1 Planning

```text
flower update --plan
```

The plan includes:

- current and target versions;
- dependency changes;
- module compatibility;
- manifest migrations;
- generated-file diffs;
- database migrations;
- ownership conflicts;
- required approvals;
- verification commands;
- rollback limitations.

The plan receives a stable ID and digest.

### 21.2 Applying

```text
flower update --apply <plan-id>
```

Flower refuses to apply when:

- the project changed after planning;
- the plan digest is invalid;
- generated files were manually modified without resolution;
- module versions are incompatible;
- required database verification is unavailable;
- ownership rules would be violated.

### 21.3 Generated-file merging

Flower records the previous generated base and supports:

- replace when the project copy is unchanged;
- three-way merge when both framework and project changed;
- explicit project ownership transfer;
- ejection from future management.

## 22. Security baseline

Security is a release gate, not optional guidance.

### 22.1 Application requirements

- Secure session validation for protected routes.
- Organization-scoped membership authorization.
- RLS on tenant-owned database tables.
- Tests covering owner, member, anonymous, cross-tenant, and service-role access.
- Durable rate limiting for authentication and paid APIs.
- Per-user or per-organization quotas for AI usage.
- Structured logging with secret and personal-data redaction.
- No request-body logging for authentication, AI prompts, or sensitive forms.
- Secure headers including CSP, frame restrictions, content-type protection, referrer policy, and permissions policy.
- Explicit file-upload type, size, and ownership validation.
- Service-role clients restricted to server-only allowlisted operations.
- Auditing for role, membership, security, and destructive business changes.

### 22.2 Supply-chain requirements

- Lockfiles committed and verified.
- Official templates and modules signed or checksum-verified.
- Installers pinned to immutable versions.
- No `latest` dependencies in release automation.
- Dependency audit thresholds enforced in CI.
- Secret scanning and license checks.
- CI actions pinned to full commit digests for released templates.

### 22.3 Agent requirements

- Agents cannot approve their own consequential actions.
- Generated agent instructions cannot grant access beyond the active environment.
- External writes, pushes, deployments, and production migrations require explicit workflow steps.
- Prompt files are treated as untrusted data when loaded from external sources.
- Local agent memory is excluded from version control.

```text
type-check

```

### 23.2 Testing levels

- Unit tests for pure domain and framework logic.

## 24. Documentation and decisions

Flower uses three documentation categories:

1. **Generated reference:** derived from manifests, schemas, routes, and modules.
2. **Human context:** product goals, audience, terminology, non-goals, and current focus.
3. **Architecture decisions:** durable records of consequential technical choices.

Architecture decision files include:

```text
id
status
date
context
decision
consequences
alternatives
reviewDate
```

Documentation debt may be tracked, but normal commits must not be blocked by an easily bypassed text marker. CI should instead validate required generated docs and decision records for specifically classified changes.

## 25. Cross-platform requirements

Flower's CLI must be implemented with cross-platform Node APIs.

- No required Bash scripts.
- No reliance on `sed`, `grep`, `awk`, `/tmp`, or Unix path behavior.
- All path comparisons use resolved platform-native paths.
- Child processes use argument arrays rather than shell-built strings.
- Windows, macOS, and Linux run in CI.
- Temporary files use operating-system temporary directories.
- Destructive operations verify targets are inside the intended project.
- Project setup never requires globally installed packages.

## 26. Observability and privacy

Flower itself collects no telemetry by default.

Local journals contain:

- command name;
- Flower version;
- plan ID;
- changed paths;
- step results;
- error codes;
- verification results.

Journals must not contain:

- environment values;
- tokens or passwords;
- raw AI prompts;
- uploaded private documents;
- database records;
- complete command output when it may contain secrets.

Optional telemetry requires explicit opt-in and a published data contract.

## 27. Versioning policy

Flower follows semantic versioning.

- Kernel and CLI share a release version initially.
- Modules version independently.
- Schemas have explicit integer versions.
- Workflow definitions have independent schema and workflow versions.
- Compatibility ranges are machine checked.
- Breaking configuration changes require a manifest migration.
- Breaking generated-code changes require an upgrade migration and release note.

## 28. MVP definition

Flower 0.1 is complete when it can:

1. Initialize a TypeScript Next.js/Supabase project on Windows, macOS, and Linux.
2. Validate `.flower/project.json`, lock state, and ownership rules.
3. Install `auth`, `organizations`, `rbac`, and `audit` modules.
4. Generate safe composition code and Codex/Claude adapters.
5. Run architecture and security checks.
6. Apply migrations to an isolated test database.
7. Prove tenant isolation through automated RLS tests.
8. Produce and apply a versioned update plan.
9. Resume or explain a partially failed workflow.
10. Eject a module without corrupting the project.

The MVP deliberately excludes AI chat, scheduling, billing, analytics, BIR, marketing automation, and production deployment automation.

## 29. Implementation roadmap

### Phase F0 — Repository and contracts

- Create the Flower repository and workspace.
- Establish package boundaries and TypeScript configuration.
- Define project, lock, ownership, module, workflow, and migration schemas.
- Implement structured errors and stable JSON output.
- Add Windows/macOS/Linux CI.

**Exit criteria:** schemas validate fixtures; packages build; CLI prints version/help; CI is green on all platforms.

### Phase F1 — Kernel and diagnostics

- Manifest loader and schema migration framework.
- Mode detection from manifest.
- Ownership matcher and protected-path validation.
- `flower doctor`, `flower validate`, and `flower status`.
- Local journal with redaction.

**Exit criteria:** valid and invalid golden projects produce deterministic diagnostics and exit codes.

### Phase F2 — Initialization and template

- Thin Next.js/Supabase template.
- Transactional `flower init`.
- Dry-run and JSON plans.
- Package-manager abstraction.
- Template digest verification.

**Exit criteria:** clean projects initialize and pass tests, type-check, lint, and build on all supported platforms.

### Phase F3 — Module engine

- Module manifest loader.
- Dependency/conflict resolver.
- Add, remove, and eject operations.
- Generated-file tracking and checksums.
- Initial auth/organizations/RBAC/audit modules.

**Exit criteria:** modules compose correctly and removal/ejection scenarios pass golden-project tests.

### Phase F4 — Database and security

- Migration registry and planner.
- Isolated Supabase/Postgres test environment.
- RLS policy test helpers.
- Security baseline generator and validator.
- Secret and dependency scan integration.

**Exit criteria:** cross-tenant access tests fail safely, module migrations verify, and insecure policies block release checks.

### Phase F5 — Workflows and adapters

- Typed workflow engine.
- Approval and journal steps.
- Codex and Claude adapter generation.
- CI adapter generation.
- Drift validation.

**Exit criteria:** the same canonical workflow produces consistent adapters and cannot bypass approval or ownership rules.

### Phase F6 — Updates

- Version resolver.
- Update planning and plan digests.
- Generated-file three-way merge support.
- Manifest and module migrations.
- Upgrade scenario test matrix.

**Exit criteria:** a 0.1-to-0.2 fixture updates reproducibly, detects conflicts, and preserves project-owned code.

## 31. Success measures

Flower is succeeding when:

- a developer can explain which code Flower owns and which code the project owns;
- an update never silently overwrites project domain code;
- enabled modules agree across manifest, packages, database, navigation, and tests;
- tenant isolation failures are caught before deployment;
- Windows setup is as reliable as Unix setup;
